## 2. Проект простыми словами

equa.ai помогает платёжному сервису выбрать действие для подозрительного платежа:
**разрешить, дополнительно проверить или заблокировать**.

Блокировать всё подозрительное нельзя: честные клиенты теряют возможность платить.
Пропускать всё тоже нельзя: мошенники причиняют убытки.
Мы оцениваем риск и сравниваем ожидаемую стоимость каждого действия.
Аналитик видит причины решения и может проверить влияние настроек на результаты.

Пример: покупатель обычно тратит 20 000 ₸, но сейчас платит 180 000 ₸ в поездке.
Необычная операция не обязательно означает мошенничество. При подходящих условиях
дополнительная проверка выгоднее немедленной блокировки.

**Покупатель продукта:** финтех-компания/платёжный сервис; возможный более поздний клиент — банк.
**Основной пользователь:** антифрод-аналитик или риск-менеджер.
**Получатель пользы:** честный владелец карты/кошелька, чьи платежи реже блокируют ошибочно.
Это позиционирование и гипотезы из кейса, ещё не подтверждённые интервью с клиентами.

Фраза для защиты:
> equa.ai помогает платёжным сервисам бороться с мошенничеством, сохраняя удобство
> честных клиентов. Мы показываем риск, предлагаем действие и объясняем его экономический смысл.

## 6. Точный смысл модели и экономики

Признаки:
1. `log(1 + amount / average_amount)`.
2. Другая страна относительно обычной.
3. Новое устройство.
4. `log(1 + frequency - 1)`, где frequency включает текущую операцию.
5. Категория перевода.
6. Взаимодействие «другая страна × новое устройство».

В генераторе время растёт, средний чек и окно 10 минут вычисляются ДО текущей
операции. Для нового клиента используется сгенерированный стартовый профиль.
В ручном симуляторе пользователь сам вводит агрегаты истории — временное упрощение.

Метки генерируются вероятностно из логистической зависимости. Поэтому
**генератор благоприятен для нынешней модели**; нельзя использовать его результаты
как доказательство качества на настоящем фроде или превосходства над конкурентами.

XAI не использует SHAP/LLM. После калибровки модель всё ещё линейная в log-odds.
В API есть baseline и все вклады; их сумма восстанавливает log-odds риска.
Top-3 в UI — положительные и отрицательные вклады по абсолютной величине.
Это не проценты и не причинно-следственное доказательство мошенничества.

Обозначения: p — риск, A — сумма, B — стоимость ложной блокировки,
C — стоимость проверки, a — отказ честного клиента, e — эффективность проверки.

```text
Approve   = p × A
Challenge = C + (1-p) × a × B + p × (1-e) × A
Block     = (1-p) × B
```

По умолчанию: B=2500 ₸, C=25 ₸, a=0.05, e=0.90. Это допущения, не банковская статистика.
В backtest используются известные метки, но эффект Challenge остаётся ожидаемым.
Предполагается, что Block полностью предотвращает текущую операцию.

FPR = честные Block / все честные операции. Challenge не равен ложной блокировке.
Precision/Recall в API считают подозрительными и Challenge, и Block.
`pr_auc` в коде вычисляется как `average_precision_score`, это именно average precision.
Brier score также доступен в метаданных.

Baseline правил: Block при другой стране + новом устройстве либо сумме >5 средних
чеков; Challenge при другой стране или новом устройстве; иначе Approve.
Пороговый baseline: Challenge от 12%, Block от 55%. Пороги сейчас не оптимизированы.

При дефолтах на текущем генераторе интерфейс показывал примерно:
20 000 тестовых операций, 1% фрода, AP 0.184, 78 честных блокировок, 5666 проверок,
оценка общих потерь equa 2.35 млн ₸. Это снимок демонстрации, а не целевые KPI.
Любые изменения данных/версии модели требуют пересчёта, а не сохранения этих чисел.

## 7. API-контракт текущего MVP

| Маршрут | Метод | Назначение |
| --- | --- | --- |
| `/api/health` | GET | Готовность процесса, выбранный адаптер, synthetic |
| `/api/report` | POST | Policy в JSON → metadata, policy, strategies, stress |
| `/api/transactions?page=1&action=all&query=` | POST | Policy в JSON → items, total, page, page_size=12 |
| `/api/score` | POST | transaction + policy → risk, action, costs, explanations, id |
| `/api/history` | GET | Последние 30 записей decisions |
| `/api/decisions/{uuid}/challenge` | POST | outcome passed/failed → сохранение демо-исхода |

Пример POST `/api/score`:

```json
{
  "transaction": {
    "amount": 180000,
    "average_amount": 35000,
    "country": "TR",
    "home_country": "KZ",
    "new_device": false,
    "frequency": 1,
    "merchant": "travel"
  },
  "policy": {
    "block_cost": 2500,
    "challenge_cost": 25,
    "abandonment": 0.05,
    "effectiveness": 0.9
  }
}
```

Допустимые страны: KZ/TR/DE/US/BR; категории: retail/travel/digital/transfer.
Ограничения текущей схемы: сумма >0 и ≤10 млн; средний чек 100…10 млн;
frequency 1…100; вероятности 0…1. Бизнес-лимиты см. в schemas.py.
Ошибочный ввод: 422. Ошибка SQL: 503. Повторный/неподходящий challenge: 409.
`/api/health` **не проверяет доступность Supabase**, только выбранный режим.

Таблица decisions: UUID, created_at, transaction_data, policy_data, result_data,
action, challenge_outcome. SQLite хранит JSON как текст, PostgreSQL — JSONB.
Исходное решение не переписывается после challenge; исход хранится отдельно.
UPDATE challenge условный и атомарный, повторное прохождение запрещено.

## 10. Ограничения и задачи, которые нельзя выдавать за готовые

1. Нет датасета организаторов, импорта CSV, проверки схемы и отчёта о качестве данных.
2. История клиента в ручном скоринге задаётся извне, а не вычисляется доверенным сервером.
3. Нет IP/Geo/device_id/merchant_id/link analysis из полного кейса.
4. Обучение выполняется на старте; нет сохранённого артефакта, fingerprint данных и реестра запусков.
5. Нет оптимизированного порогового baseline и отдельного validation-набора для его настройки.
6. Stress — только анализ чувствительности. Робастная/minimax-политика не реализована.
7. Нет выгрузки XAI-отчёта для аналитика/поддержки.
8. Нет auth, RBAC, лимитов запросов и изоляции организаций. До публичного деплоя требуется отдельный проход.
9. Supabase не подключён; миграция/адаптер не тестировались на реальном облаке.
10. Нет настоящих исходов Challenge; нельзя заявлять измеренное снижение отказов/фрода от 2FA.
11. Политика и фильтры не переживают перезагрузку; URL сохраняет только экран.
12. Нет idempotency key для POST score; повторная отправка может создать новую запись.
13. Поиск по тестовым операциям линейный в памяти; не позиционировать это как масштабируемый продакшен.
14. Тест UI добавляет синтетические ручные решения в текущую локальную историю.
15. Нет презентации, резервного видео, клиентских интервью и подтверждённой бизнес-модели.

Потенциальные инженерные проверки, а не уже воспроизведённые дефекты:
при частых пересчётах проверить гонки запросов политики, закрытие SQLite-соединений,
согласованность URL/фильтров, повторный вход на экран и ошибки загрузки bundle.

## 11. Инновационность: что можно защищать честно

Три действия, риск и XAI уже существуют в индустрии. В исследовании контекста
Stripe прямо описывал выбор вмешательств по ожидаемым результатам:
https://stripe.com/guides/optimizing-payments-at-scale.
Не говорить «мы первые придумали дополнительную проверку» или «аналогов нет».

Предлагаемый акцент equa: понятная лаборатория, где небольшой финтех проверяет
экономику своих настроек и видит, при каких допущениях результат перестаёт быть выгодным.
Усиление: робастный выбор политики на нескольких сценариях и честное сравнение
на отложенных данных. Это следующая гипотеза разработки, не завершённая инновация.

Не обещать конкретный процент экономии, мировое лидерство, production-ready,
реальную банковскую интеграцию или действующие платные клиенты без доказательств.
