# equa.ai — локальный тестовый MVP

Антифрод-лаборатория для Overclock Hackathon 2026, трек FinTech.
Все данные синтетические; реальные платежи, банки и 2FA не подключены.

## Запуск на Windows

Из корня проекта (Python 3.12 или новее):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Если окружение уже установлено, достаточно последней команды.
Откройте http://127.0.0.1:8000. Документация API: http://127.0.0.1:8000/docs.
Первый запуск обучает модель на 100 000 строках и может занять несколько секунд.
Остановка: Ctrl+C в терминале сервера.

## Фронтенд

- `frontend/index.html` — пять рабочих экранов, формы и доступная HTML-разметка.
- `frontend/styles.css` — цвета, сетки, компоненты и адаптация для узкого экрана.
- `frontend/app.js` — переключение экранов, запросы к Python, отрисовка результатов.

Основной фронтенд написан на HTML/CSS/JavaScript. Magic UI и React Bits подключены
как небольшие React-компоненты внутри существующего интерфейса. Тема — тёмная,
с фиолетовыми акцентами; референсы лежат в `design/`, токены описаны в `DESIGN.md`.
После редактирования HTML/CSS или `app.js` обновите страницу. При изменении React:

```powershell
npm ci
npm run build
```

Готовый `frontend/dist/enhancements.js` включён в проект, поэтому для обычного
локального запуска хватает Python. Бэкенд пока не расширяется по запросу команды.

### Инструменты фронтенда

- `npm run browser -- -s=equa open http://127.0.0.1:8000` — Playwright CLI.
- `npm run browser -- -s=equa run-code --filename tools/verify-frontend.js` — UI-проверки
  (создайте папку `output/playwright` заранее).
- `node tools/reactbits-client.mjs` — проверенный MCP-клиент к React Bits. Нужен интернет
  для получения исходника компонента. Глобальный конфиг Codex не изменяется.
- `npm run reactbits` — локальный React Bits MCP Server по stdio.

Magic UI NumberTicker форматирует значения; React Bits FadeContent показывает
пояснение нового результата за 180 мс. Клавиатурные действия и reduced motion
показывают результат без декоративной анимации. Лицензии: `THIRD_PARTY.md`.

В коде есть русские комментарии к назначению файлов, функциям и важным расчётам.

### Что можно проверить в интерфейсе

1. **Обзор:** сравнить ожидаемую стоимость трёх стратегий на 20 000 тестовых операций.
2. **Транзакции:** поиск по операции/клиенту, фильтр решения, страницы по 12 строк.
3. **Проверить платёж:** выбрать обычную покупку, поездку или подозрительную серию;
   рассчитать риск и посмотреть стоимость каждого действия.
4. **Лаборатория:** изменить стоимость ошибок и эффективность проверки, нажать
   «Пересчитать стратегии». Изменение слайдера без этой кнопки не применяется.
5. **История:** последние 30 ручных решений, сохранённых в SQL. Журнал тестовой
   выборки и история ручных проверок — разные наборы данных.

## Как соединены компоненты

```text
Браузер (HTML/CSS/JS)
        | HTTP /api/*
        v
Python / FastAPI
        |-- ML: риск и вклады признаков
        |-- Политика: стоимость Approve / Challenge / Block
        |-- SQL-хранилище: SQLite локально, Supabase PostgreSQL позже
```

- `backend/main.py` — маршруты API и запуск модели один раз при старте.
- `backend/schemas.py` — проверка полей запроса, диапазонов и типов.
- `backend/engine.py` — генерация данных, обучение и сравнение стратегий.
- `backend/storage.py` — параметризованные SQL-запросы и адаптер Supabase REST.
- `sql/local.sql` — локальная таблица истории решений.
- `supabase/migrations/202609160001_decisions.sql` — схема для PostgreSQL.
- `run.py` — запуск единого локального сервера на порту 8000.

## Что сейчас работает локально

SQLite создаёт `data/equa.db` автоматически. В историю пишутся параметры платежа,
политика, риск, вклады признаков и результат демо-проверки. История сохраняется
при перезапуске. Тестовые 100 000 транзакций генерируются в памяти с фиксированным
seed=2026 и не загружаются в SQL. Модель также обучается заново при старте.

## Позже: Supabase / PostgreSQL

Облачный проект пока не создан и интеграция с реальным Supabase не проверялась.
Код адаптера и SQL-миграция подготовлены; они не означают выполненного подключения.

1. Создайте Supabase-проект и выполните SQL из `supabase/migrations/202609160001_decisions.sql`
   в его SQL Editor.
2. Скопируйте `.env.example` в `.env`.
3. Установите `DATABASE_MODE=supabase`, `SUPABASE_URL` и серверный ключ
   `SUPABASE_SERVICE_ROLE_KEY` (legacy service_role JWT или новый secret key).
4. Перезапустите Python. Новые ручные решения будут сохраняться в PostgreSQL.

Ключ нельзя вставлять в JavaScript или коммитить. `.env` исключён из Git.
RLS закрывает таблицу от anon/authenticated; её читает и пишет только сервер.
Существующая SQLite-история автоматически не переносится. Сбой Supabase не
подменяется успешной локальной записью. FastAPI размещается отдельно от Supabase.

## Как работает модель и что означают цифры

Используется Logistic Regression + Platt-калибровка, а не LLM и не SHAP.
Признаки: отношение суммы к среднему чеку, другая страна, новое устройство,
частота, категория перевода и взаимодействие страны с новым устройством.
Средний чек и частота в генераторе рассчитываются только по прошлым операциям.
Для нового клиента стартовый средний чек берётся из синтетического профиля.
В ручном симуляторе эти поля вводит пользователь — это упрощение демо.

Временное разделение: 60% обучение, 20% калибровка, 20% тест.
Метки вероятностные и не используются как входные признаки. Генератор построен
на похожей логистической зависимости: результаты на нём не доказывают переносимость
на реальные данные или неизвестные виды фрода.

Объяснение — точный вклад признака в log-odds относительно среднего профиля
обучения; сумма всех вкладов и baseline восстанавливает log-odds модели.
Интерфейс показывает три наиболее сильных вклада. Это не проценты и не причинность.

При вероятности фрода p, сумме A, цене ложной блокировки B, цене проверки C,
доле отказов честных клиентов a и эффективности проверки e:

```text
Approve   = p * A
Challenge = C + (1-p) * a * B + p * (1-e) * A
Block     = (1-p) * B
```

Выбирается минимальная ожидаемая стоимость. В backtest вместо p используются
известные метки, но эффект Challenge остаётся ожидаемым, поскольку реальных
исходов 2FA нет. Предполагается, что Block полностью останавливает текущий платёж.
FPR — ошибочные блокировки / все честные операции; Challenge не считается Block.
Precision/Recall в API считают подозрительными Challenge и Block вместе.
PR-AUC отображает average precision; Brier score также доступен в API.

Baseline «Простые правила»: Block при другой стране + новом устройстве или
сумме больше 5 средних чеков; Challenge при другой стране или новом устройстве.
Baseline «Фиксированный порог»: Challenge от 12%, Block от 55%.
Это иллюстративные, не оптимизированные конкуренты; сравнение не доказывает
превосходства над коммерческими продуктами.

В стресс-тесте исходные действия каждой стратегии зафиксированы. Меняется
эффективность проверки: 95%, 75%, 50%. Это анализ чувствительности, а не
автоматическая робастная оптимизация. Политика пока не оптимизирует худший сценарий.

## Ограничения тестовой версии

Нет банковской интеграции, настоящей 2FA, авторизации, импорта датасета организаторов
и публичного деплоя. Подтверждение кнопкой в симуляторе — только демо.
Сервер слушает только 127.0.0.1. Перед публичным использованием необходимы
авторизация и разграничение доступа. Не вводите реальные банковские данные.
