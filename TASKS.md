# equa.ai — план завершения и разделение работы

Это предлагаемый план, а не список выполненных функций. Актуально на 16.09.2026.

Сначала прочитать `HANDOFF.md`. Последний приоритет пользователя — фронтенд;
возвращение к ML/бэкенду согласовать в назначении следующего этапа.

## 1. Что считаем готовым конкурсным MVP

- На данных кейса можно загрузить операции, получить риск и объяснение.
- История и признаки считаются без доступа к будущим событиям и меткам фрода.
- Три стратегии сравниваются на одном и том же ранее не использованном тесте.
- Стоимость неудобства и эффект проверок явно помечены как допущения.
- Есть хотя бы одно обоснованное отличие, которое демонстрируется работающей функцией.
- На новом компьютере проект запускается по README; жюри имеет согласованный доступ к демо.
- Есть презентация ≤12 слайдов, видео ≤3 минут и размещение в AI Startify.
- Каждый участник может объяснить свою часть и общую цепочку решения.

## 3. Конкретные технические шаги

### Данные и ML

1. Установить, какие реальные поля есть: идентификатор клиента, время, amount,
   merchant, device, country, IP/Geo и label. Не придумывать отсутствующие поля.
2. Написать адаптер схемы и отчёт качества. Размер, кодировка, валюта, пропуски,
   дубли, распределение меток, временной диапазон.
3. Выделить `dataset`, `features`, `train`, `evaluate`; текущий engine можно
   постепенно разнести, не переписывая публичный API сразу.
4. Разделить время на train / calibration / policy-validation / final-test.
   Текущие 60/20/20 не оставляют независимого набора для настройки новых политик:
   выделить validation внутри первых 80% или использовать временную nested-схему.
5. Признаки только из прошлого; исключить label, постфактум-исходы и утечки клиента.
   При равных timestamps задать воспроизводимый порядок без заглядывания вперёд.
6. Сохранить логистическую регрессию как объяснимый baseline. При наличии времени
   сравнить CatBoost/LightGBM, а не автоматически считать их лучше.
7. Для нелинейной модели использовать SHAP или другой проверенный метод,
   не оставлять объяснения от старой линейной модели.
8. Сохранить артефакт, feature schema, версии, seed, fingerprint данных и отчёт.
   Не загружать произвольные pickle/joblib-файлы от пользователя.

### Экономика и инновационная часть

1. Выбрать пороги baseline на validation по той же функции потерь, что equa.
2. Считать фрод в сумме денег и количестве операций; отдельно FPR блокировок,
   долю Challenge, AP, precision/recall и калибровку вероятности.
3. Не считать известными эффект 2FA, отток и стоимость недовольства, если данных нет.
4. Добавить сценарии по e и a. Для робастного режима можно выбирать одну политику
   из ограниченного набора по минимальному худшему cost или minimax regret
   на validation; явно документировать выбранный критерий.
5. Не подбирать лучший сценарий после просмотра final-test.
6. Сравнивать nominal и robust на одном тесте. Показывать, где робастность увеличила
   среднюю стоимость ради меньшего риска в плохом сценарии; не скрывать проигрыши.
7. Не превращать это в заявление о причинном эффекте без эксперимента/данных об исходах.

### Python API и SQL

1. Согласовать API до параллельных UI-правок. Сохранить текущие /score и /report
   или сделать совместимую миграцию.
2. Добавить идентификаторы dataset/model/policy в отчёты и решения.
3. Импортировать историю с контролем размера, типов и формата; не принимать
   неограниченный файл в память. Не доверять клиентским агрегатам в будущем рабочем API.
4. Экспортировать объяснение из сохранённого решения, чтобы оно не менялось при обновлении модели.
5. Для Supabase — SQL-миграции в Git, JSONB, server-only ключ, проверка доступа anon.
   SQLite остаётся способом быстрого локального запуска.
6. Добавить idempotency для повторного POST score и тест атомарности challenge.
7. Для публичного демо отдельно решить авторизацию/режим песочницы, лимиты,
   безопасные ошибки, секреты и изоляцию данных. Не публиковать нынешний localhost как production.

### Фронтенд

1. Сохранить текущие рендеры/цвета/пять экранов.
2. Добавить загрузку данных, состояния проверки файла и источник набора в отчёте.
3. Добавить скачивание объяснения и метаданные модели в карточке решения.
4. Разделять расчётный риск, выбранное действие, факт метки и исход демо-проверки.
5. При добавлении сохранённых политик показать отличие черновика от применённой версии.
6. Проверить гонки запросов и двойные клики; результат должен относиться к тем
   параметрам, которые видит пользователь.
7. Хранить экран/фильтры в URL при необходимости; не внедрять новый роутер ради одной функции.
8. Проверить клавиатуру, reduced motion, читаемость, 390/768/1440px, состояния ошибок.

## 4. Разделение команды или моделей

Реальные имена и компетенции неизвестны. Назначить ответственных вместо вымышленных участников.

| Поток | Зона владения | Результат |
| --- | --- | --- |
| A: данные/ML | engine и новые модули данных/обучения, ML-тесты | Артефакт модели, отчёт качества, сравнение |
| B: Python/SQL | main, schemas, storage, sql, supabase, API-тесты | Стабильные контракты, импорт/экспорт, сохранение |
| C: фронтенд | frontend, React-компоненты, UI-проверки | Подключённые экраны и проверенный UX |
| D: продукт/защита | интервью, презентация, видео, AI Startify | Обоснование боли, понятное демо, пакет сдачи |

При двух участниках: A+B и C+D. При трёх: A, B, C+D.
При работе нескольких моделей: отдельные ветки/рабочие копии, а не одновременная
запись в один и тот же файл. Один интегратор отвечает за сборку и main.

Порядок синхронизации:

1. B публикует контракты и примеры JSON; A подтверждает доступные поля.
2. C подключает UI к этим контрактам. Тестовые ответы явно маркируются как mock.
3. A отдаёт модель и метаданные B; B подключает inference без обучения на запросе.
4. D использует только результаты последнего общего отчёта, не старые скриншоты.
5. После интеграции — сборка и основные UI/ML/SQL-проверки. Обновить HANDOFF/TASKS.

Каждая задача закрывается сообщением: что изменено, какие файлы, как проверено,
ограничения, commit/PR. Не объявлять «готово» по одному успешному запуску скрипта.

## 6. Презентация: до 12 слайдов

1. equa.ai: кому и какую задачу решаем, одна фраза.
2. Боль: потерянные деньги и ошибочно отклонённые честные платежи.
3. Пользователь/покупатель, что удалось подтвердить разговорами.
4. Сценарий: необычная честная покупка и путь проверки.
5. Система: данные → риск → стоимость → действие → объяснение.
6. Данные и ML: объём, признаки, разделение, отсутствие утечки.
7. Результаты против честных baseline, метрики и условия расчёта.
8. Отличие: сценарная/робастная лаборатория, только реально реализованное.
9. Работающий MVP: ключевые экраны и QR/ссылка.
10. Внедрение и бизнес-модель как гипотеза: пилот, API, оплата за объём/подписка без вымышленных продаж.
11. Ограничения, следующий эксперимент и план развития.
12. Команда, вклад каждого, GitHub/демо/AI Startify.

## 7. Демо до 3 минут

- 0:00–0:20 — одна понятная проблема.
- 0:20–1:00 — покупка в поездке, риск, проверка, объяснение.
- 1:00–1:30 — подозрительная серия, блокировка, причины.
- 1:30–2:15 — сравнение стратегий и изменение бизнес-параметров.
- 2:15–2:40 — стресс-сценарий, честные ограничения.
- 2:40–3:00 — ценность, ссылки, завершение.

Никаких заранее вбитых «результатов» вместо работающих вычислений. Для сбоя интернета
иметь локальный запуск и записанное резервное видео.
